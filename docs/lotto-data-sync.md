# LOTTO LAB 데이터 동기화

## 공식 소스와 파싱

기준은 [동행복권 로또6/45 결과](https://www.dhlottery.co.kr/lt645/result)입니다. 2026-09-27 확인 당시 페이지의 회차 선택 목록에는 1회차부터 최신 완료 회차까지 있으며, 페이지 스크립트는 같은 도메인의 `/lt645/selectPstLt645InfoNew.do`에 `srchDir=center`, `srchLtEpsd=<회차>`를 GET으로 보냅니다. 응답의 `data.list`에서 `ltEpsd`(회차), `ltRflYmd`(YYYYMMDD), `tm1WnNo`~`tm6WnNo`를 읽습니다. `bnsWnNo`는 무시합니다. HTML의 선택 목록은 최신 회차 확인에만 사용합니다. 이 내부 응답은 공식 사이트가 사용하는 형식이지만 변경되지 않는 공개 API 계약은 아닙니다.

## 전체·증분 실행

`.env.local`의 Supabase 환경변수와 `db:setup` 검증을 준비한 뒤 다음 명령을 실행합니다.

```bash
npm run lotto:sync:all
npm run lotto:sync
```

전체 명령은 공식 1회차부터 최신 완료 회차까지 조회하고 빠진 회차를 채웁니다. 증분 명령은 DB의 최대 완료 회차 다음부터 조회합니다. 공식 JSON은 10회차 묶음으로 수신하며 모든 응답을 파싱하고 요청 범위의 회차 연속성과 날짜 순서를 검증한 다음 DB 저장을 시작합니다. 번호는 1~45의 중복 없는 정수 6개, 날짜는 실제 달력 날짜여야 합니다.

## Supabase PostgreSQL 흐름과 결과

각 완료 회차는 `lotto_draws`에 저장합니다. 같은 회차·날짜·번호가 있으면 결과 비교를 재확인하고 건너뛰며, 다르면 오류로 중단합니다. 해당 회차에 추천이 있으면 각 추천의 당첨번호 일치 개수를 `lotto_results.match_count`에 기록합니다. 현재 Supabase 스키마에는 보너스번호·보너스 일치·등수 컬럼이 없으며 분석과 화면도 사용하지 않습니다.

최신 완료 회차 다음 번호를 7일 뒤 날짜의 `open` 회차로 생성합니다. 기존 open 회차가 있으면 번호와 날짜가 일치하는지 검증하고 중복 생성하지 않습니다. 추천은 이 open 회차를 대상으로만 저장됩니다.

## 안전성과 복구

공식 소스 접근 실패나 응답 검증 실패는 DB 쓰기 전에 중단됩니다. Supabase HTTP 요청은 회차 저장·결과 비교·다음 open 생성 사이에서 하나의 DB 트랜잭션이 아닙니다. 중간 실패 시 이전에 저장된 회차·추천·결과를 삭제하지 않으며, `npm run lotto:sync:all`을 다시 실행하면 동일한 완료 회차를 확인하고 결과 비교를 재실행할 수 있습니다. 오류가 난 회차 이후는 처리하지 않습니다. 저장된 공식 값이 불일치하면 운영자가 원본과 DB를 직접 조사해야 합니다. 공식 사이트 내부 응답 구조가 달라졌다면 `lib/lotto/source.ts` 파서를 수정하고 실시간 응답과 테스트를 재검증합니다. 수동 복구에는 `npm run lotto:import -- <공식 확인 JSON 파일>`을 사용합니다.

## 향후 Synology DSM 자동화

DSM 작업 스케줄러에서 사이트 프로젝트 디렉터리로 이동해 토요일 결과 게시 후 `npm run lotto:sync`를 실행하도록 등록할 수 있습니다. CLI는 대화형 입력 없이 종료 코드 0/1과 요약 또는 오류를 출력합니다. 실제 DSM 일정 등록은 이 저장소의 범위 밖입니다.
